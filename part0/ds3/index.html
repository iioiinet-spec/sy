1.1 알고리즘은 맞았는데 떨어진 경우

수 100만 개를 읽어 합을 구하는 문제가 있다고 하자. 풀이는 누가 봐도 O(N) 한 번 훑기이고, 더 빠를 수가 없다. 그런데 제한 시간이 빠듯하면 읽는 데만 시간을 다 쓰고 떨어진다. 교재의 예시 측정 환경에서는 다음과 같은 값이 나왔다고 가정해 보자(기기·컴파일러·입력 데이터에 따라 달라진다).

하는 일100만 개 기준설명
scanf로 읽기약 47 ms형식 문자열을 100만 번 해석한다
버퍼로 읽기약 21 ms통째로 가져와 한 글자씩 뜯는다
printf로 쓰기약 32 ms역시 형식 해석 비용
버퍼로 쓰기약 8 ms4배 차이

100만 개에서 수십 밀리초라면 큰일은 아니다. 문제는 입력이 1,000만 개로 늘면 입출력 비용도 대체로 함께 늘어난다는 점이다. 표의 수치를 선형으로 어림하면 입력만 각각 약 0.47초와 0.21초다. 다만 실제 시간은 파일 크기·저장 장치·측정 환경에 따라 달라지므로, 이 값만으로 통과 여부를 확정할 수는 없다.

2.1 컴파일 옵션 네 개

이 교재의 표준 빌드 명령은 다음 하나로 고정한다. 36장 끝까지 바뀌지 않는다.

gcc -std=c11 -O2 -Wall -Wextra main.c -o main
옵션하는 일빼면 생기는 일
-std=c11사용할 언어 규격을 C11로 지정한다GCC의 기본 언어 규격(예: GNU 확장 포함 모드)이 적용될 수 있다. 표준 기능만 쓰는 코드라면 차이가 없을 수도 있다
-O2컴파일러 최적화 수준 2를 사용한다속도 차이는 코드·컴파일러에 따라 다르며 더 빠르거나 비슷하거나 일부 느릴 수도 있다. 채점기의 빌드 옵션은 대회별로 확인한다
-Wall대표적인 의심스러운 코드를 경고한다일부 초기화 오류와 반환 관련 문제 등을 발견할 기회가 줄어든다. 모든 오류를 검출하는 것은 아니다
-Wextra경고를 더 켠다부호 비교, 쓰지 않는 매개변수 등을 놓친다

경고 0개가 통과 기준이다

경고는 “틀렸다”가 아니라 “수상하다”는 신호다. 그런데 대회에서 나는 버그의 상당수가 미리 경고로 떠 있던 것들이다. 경고가 하나라도 뜨면 제출 전에 전부 없앤다를 규칙으로 삼는다. 경고를 끄는 옵션(-w)은 쓰지 않는다.

자주 보게 될 경고 하나 — scanf의 반환값

scanf 반환값을 확인하지 않으면, 일부 시스템에서 _FORTIFY_SOURCE 등 추가 설정에 따라 아래 경고가 나올 수 있다. -Wall -Wextra만으로 항상 발생하는 경고는 아니다.

warning: ignoring return value of 'scanf' declared with
attribute 'warn_unused_result' [-Wunused-result]

scanf는 제대로 읽은 항목의 개수를 돌려주는데 그것을 버렸다는 뜻이다. 입력이 예상과 다르면 변수가 쓰레기값인 채로 넘어가므로, 확인하는 편이 맞다.

/* 반환값을 확인하지 않는 코드(환경에 따라 경고 가능) */
scanf("%d", &n);

/* 경고가 없고 안전한 코드 */
if (scanf("%d", &n) != 1) return 1;   /* 못 읽으면 종료 */

고속 입력기를 쓰면 scanf의 반환값 문제는 없어지지만, 대신 입력 종료와 숫자 범위를 직접 검사해야 한다.

2.2 메모리의 세 구역

02장 연습 07에서 7.6MB짜리 지역 배열이 죽는 것을 보았다. 왜 그런지 그림으로 정리하자. 주요 데이터 저장 영역은 초보자 관점에서 스택, 정적 저장 영역(전역·정적 변수), 힙으로 구분할 수 있다. 실제 프로그램에는 코드 영역 등도 있다.

내 환경의 스택 크기 확인하기

$ ulimit -s
8192          ← 단위는 KB 이므로 8192 KB = 8 MB

위 예시 환경은 스택 한도가 약 8MiB이지만, 배열 하나에 8MiB 전체를 쓸 수 있다는 뜻은 아니다. 함수 호출에 필요한 다른 공간도 사용하며 환경마다 한도가 다르다. 대회에서는 큰 고정 크기 배열을 전역 또는 static으로 두는 것이 흔히 안전하고, 크기를 실행 중 정해야 하면 힙 할당을 고려한다.

2.3 입출력이 느린 이유

scanf("%d", &x)가 하는 일을 풀어 보면 이렇다.

  1. 형식 문자열 "%d"를 한 글자씩 해석한다 — 정수를 읽으라는 뜻이구나
  2. 공백을 건너뛰고 숫자를 모은다
  3. 모은 글자들을 숫자로 바꾼다
  4. 가변 인자 처리를 거쳐 주소에 써 넣는다

문제는 1번이다. 형식에 따른 검사·변환 및 호출 비용이 반복된다. 정수만 읽는 문제라면 일반적인 형식 처리 일부를 줄이는 방식으로 최적화할 수 있다. 고속 입력기는 이 과정을 없애고 “숫자 글자를 모아 10을 곱해 더한다”만 남긴다.

3.1 실험 — 같은 배열, 다른 자리

크기 300만(12MB)짜리 int 배열을 지역과 전역에 각각 두고 돌려 본다. 메모리 제한 256MB 기준으로는 둘 다 여유롭다.

/* f_stack.c — 지역(스택) */
#include <stdio.h>
int main(void){
    int a[3000000];          /* 12MB */
    for(int i=0;i<3000000;i++) a[i]=i;
    long long s=0;
    for(int i=0;i<3000000;i++) s+=a[i];
    printf("합 = %lld\n", s);
    return 0;
}
/* g_global.c — 전역 */
#include <stdio.h>
static int a[3000000];   /* 12MB */
int main(void){
    for(int i=0;i<3000000;i++) a[i]=i;
    long long s=0;
    for(int i=0;i<3000000;i++) s+=a[i];
    printf("합 = %lld\n", s);
    return 0;
}

두 코드의 주요 차이는 배열의 저장 영역이다

계산 내용은 글자 하나까지 같다. 그런데 하나는 죽고 하나는 산다. 이 실행 환경에서는 배열 사용량이 스택 한도를 초과했기 때문이다. 실행하자마자 죽으면 가장 먼저 큰 지역 배열을 의심한다. 입력을 읽기도 전에 죽으므로 학생들은 보통 입력 코드를 들여다보며 시간을 버린다.

주의 — 실험이 안 죽을 때도 있다

사용하지 않는 배열이나 계산은 최적화 과정에서 제거될 수 있다. 배열을 실제로 사용하도록 결과를 출력해 실험하고, 컴파일러·운영체제·스택 한도에 따라 결과가 달라질 수 있음을 기록한다. 위 코드는 GCC/Linux의 한 예이며, 모든 환경에서 같은 종료 코드가 나오는 것은 아니다.

3.2 고속 입력기 fast_in()

원리는 두 단계다. ① 입력을 최대 64KiB씩 읽어 버퍼에 담는다. ② 버퍼에서 한 글자씩 꺼내 숫자를 조립한다.

/* fastio.c — C11 표준, 범위 검사 포함 정수 입력기 */
#include <stdio.h>
#include <stdlib.h>
#include <limits.h>

#define IBUF (1 << 16)       /* 65536바이트 */
static unsigned char ibuf[IBUF];
static int ilen, ipos;

static int readc(void) {
    if (ipos == ilen) {
        ilen = (int)fread(ibuf, 1, IBUF, stdin);
        ipos = 0;
        if (ilen == 0) return -1;    /* EOF */
    }
    return (int)ibuf[ipos++];
}

static int is_space(int c) {
    return c == ' ' || c == '\n' || c == '\r' ||
           c == '\t' || c == '\f' || c == '\v';
}

/* 유효한 int 토큰 1개를 읽는다. 오류/EOF면 종료한다. */
static int fast_in(void) {
    int c = readc(), neg = 0;
    unsigned int x = 0;

    while (is_space(c)) c = readc();
    if (c == '-') { neg = 1; c = readc(); }
    else if (c == '+') c = readc();

    if (c < '0' || c > '9') {
        fputs("input missing or invalid\n", stderr);
        exit(EXIT_FAILURE);
    }

    const unsigned int limit = neg
        ? (unsigned int)INT_MAX + 1u : (unsigned int)INT_MAX;
    do {
        unsigned int d = (unsigned int)(c - '0');
        if (x > (limit - d) / 10u) {
            fputs("integer out of range\n", stderr);
            exit(EXIT_FAILURE);
        }
        x = x * 10u + d;
        c = readc();
    } while (c >= '0' && c <= '9');

    if (c != -1 && !is_space(c)) {
        fputs("invalid integer token\n", stderr);
        exit(EXIT_FAILURE);
    }
    if (neg && x == (unsigned int)INT_MAX + 1u) return INT_MIN;
    return neg ? -(int)x : (int)x;
}

3고속 입력기 (이어서)

수정된 입력기의 약속

정수는 공백으로 구분되며 INT_MIN부터 INT_MAX까지 허용한다. 탭과 줄바꿈도 건너뛰고, 입력 종료(EOF)·잘못된 토큰·범위 초과에서는 표준 오류에 메시지를 쓰고 종료한다. 숫자 뒤의 첫 구분 문자는 이미 소비한다. 별도의 반환 상태가 필요한 프로그램에서는 fast_in(int *out) 형태로 성공 여부를 반환하도록 확장할 수 있다.

세 줄만 이해하면 된다

코드하는 일
while (is_space(c))공백·탭·줄바꿈 등을 건너뛴다. is_space는 공백 문자 여섯 종류를 처리한다
if (c=='-') { neg=1; ... }음수 부호를 기억한다. 최솟값도 안전하게 읽도록 부호 없는 정수에 크기를 누적한다
x = x*10u + d핵심 한 줄. d = c - '0'로 자릿값을 구하고, 범위를 검사한 뒤 10배 하고 더한다

x*10 + (c-'0')를 손으로 따라가기 — 입력이 305일 때

시작 x = 0 → '3' : x = 0×10 + 3 = 3 → '0' : x = 3×10 + 0 = 30 → '5' : x = 30×10 + 5 = 305 → 숫자가 아닌 글자를 만나 종료.

값이 큰 입력이면 long long으로

위 함수는 int 범위만 허용하며 범위를 넘으면 명확히 오류를 낸다. 50억과 같은 값은 fast_in_ll()로 읽어야 한다. 이때도 long long으로 형만 바꾸면 끝이 아니라, 부호 없는 unsigned long long 누적값과 LLONG_MAX를 이용해 범위를 검사해야 LLONG_MIN까지 안전하다.

3.3 출력 버퍼

출력도 같은 원리다. 글자를 버퍼에 모아 두었다가 가득 찼을 때와 프로그램이 끝날 때만 한꺼번에 내보낸다.

/* fastio.c의 입력기 아래에 이어 붙이는 출력기 */
#define OBUF (1 << 16)
static char obuf[OBUF];
static int opos;

static void flush_out(void) {
    if (opos > 0 && fwrite(obuf, 1, (size_t)opos, stdout)
                    != (size_t)opos) {
        fputs("output error\n", stderr);
        exit(EXIT_FAILURE);
    }
    opos = 0;
}

static void writec(char ch) {
    if (opos == OBUF) flush_out();
    obuf[opos++] = ch;
}

static void write_int(int x) {
    char t[12];
    int k = 0;
    unsigned int u = (unsigned int)x;
    if (x < 0) {
        writec('-');
        u = 0u - u;       /* INT_MIN에도 안전한 절댓값 */
    }
    if (u == 0u) { writec('0'); return; }
    while (u > 0u) {
        t[k++] = (char)('0' + u % 10u);
        u /= 10u;
    }
    while (k > 0) writec(t[--k]);
}

절대 잊으면 안 되는 한 줄

main이 끝나기 전에 flush_out();을 반드시 부른다. 잊으면 버퍼에 남은 내용이 아예 출력되지 않는다. 출력이 적으면 한 줄도 안 나오고, 많으면 마지막 한 덩어리만 잘려 나갈 수 있다 — 예제 3에서 실제 수치로 확인한다.

왜 숫자를 거꾸로 쌓는가

x % 10으로 꺼내면 일의 자리부터 나온다. 305라면 5, 0, 3 순서다. 그래서 임시 배열 t에 거꾸로 쌓아 두었다가 뒤에서부터 꺼내 제 순서로 되돌린다. 스택과 똑같은 방식이며, 06장에서 이 패턴을 정식으로 다룬다. 부호 없는 정수로 크기를 처리하므로 INT_MIN에서도 안전하다.

왜 하필 64KB인가

버퍼가 너무 작으면 자주 내보내게 되어 효과가 줄고, 너무 크면 메모리만 차지한다. 1 << 16 = 65,536바이트는 경험적으로 알맞은 크기이고, 메모리 제한 256MB에서 부담도 없다. 입력 버퍼와 출력 버퍼를 합쳐도 128KiB다. 다만 실제 최적 크기는 환경에 따라 달라진다.

4복잡도 분석 — 입출력도 예산에 넣는다

입출력은 O(N)이지만 상수가 크다. 1초라는 예산을 어떻게 나누어 쓸지 계산해 보자.

4.1 1초 예산 쪼개기

정수 N개를 읽고, 정렬하고, N개를 출력하는 문제를 생각하자. 제한 시간은 1초다.

N입력(버퍼)정렬 O(N log N)출력(버퍼)합계여유
100,0002 ms9 ms1 ms12 ms충분
1,000,00021 ms110 ms8 ms139 ms충분
10,000,000210 ms1,300 ms80 ms1,590 ms초과

N = 1,000만이면 정렬만으로 1.3초라 애초에 다른 풀이가 필요하다. 같은 예시 비율로 scanf·printf를 사용하면 입출력은 약 790 ms(입력 470 + 출력 320), 총합은 약 2,090 ms다. 버퍼 방식의 290 ms보다 입출력에서 약 500 ms 추가되는 셈이다. 입출력을 예산에 넣지 않으면 계산이 맞아도 떨어진다.

4.2 어림 계산법

예시 환경에서의 두 어림값

  • 버퍼 입출력은 정수 100만 개당 약 20 ms — 읽기 20, 쓰기 10 정도로 기억한다
  • scanf·printf는 그 2~4배 — 100만 개당 약 50 ms, 30 ms

이 수치는 이 교재의 예시 조건에서만 초기 어림에 사용한다. 입출력은 일반적으로 O(N)이지만 데이터 길이와 환경에 따라 실제 시간의 비례 계수는 달라진다.

4.3 공간도 확인한다

입출력 버퍼는 각 64KB로 합쳐 128KB다. 메모리 제한 256MB의 0.05%이므로 신경 쓸 수준이 아니다. 오히려 주의할 것은 입력을 통째로 문자열에 담는 방식이다. 10MB짜리 입력 파일을 통으로 읽으려면 10MB짜리 배열이 필요하고, 그것을 지역 변수로 두면 3.1절처럼 즉사한다.

Q. 입력 파일 전체를 한 번에 읽는 방식이 더 빠르지 않나요?
반드시 더 빠르지는 않다. 입력 크기를 미리 알 수 없다면 배열을 넉넉히 잡거나 늘려야 하고, 그만큼 메모리를 쓴다. 64KB씩 나누어 읽는 방식은 메모리를 거의 안 쓰면서 속도의 대부분을 얻는 절충안이라 이 교재의 표준으로 삼았다.

예제 2 예산 계산

정수 500만 개를 읽어 최댓값만 출력하는 문제다. 제한 시간은 1초. (1) scanf를 쓰면 입력에 몇 ms가 드는가? (2) 통과하겠는가? (3) 버퍼 입력기를 쓰면?

풀이. 4.2절의 어림값(scanf는 100만 개당 약 50 ms, 버퍼는 약 21 ms)을 쓴다.

  • (1) 500만 ÷ 100만 × 50 ms = 약 250 ms
  • (2) 최댓값 찾기는 O(N) = 500만 번으로 약 5~50 ms. 합쳐 약 300 ms이므로 예시 측정 기준으로는 통과 가능성이 높다. 출력은 한 줄뿐이라 비중이 작다
  • (3) 500만 ÷ 100만 × 21 ms = 약 105 ms. 합쳐 약 150 ms로 여유가 두 배가 된다

교훈. 이 문제는 scanf로도 통과한다. 제한이 더 빠듯하거나 실행 환경이 느리다면 scanf와 버퍼 방식의 차이가 당락을 가를 수 있다. 예산을 계산하고 실제 입력 크기로 시간을 비교해 선택한다.

예제 3 출력이 사라진 사건

어떤 학생이 출력 버퍼를 써서 10만 줄을 출력하는 코드를 제출했더니 채점에서 “출력 형식이 다르다”가 떴다. 코드의 끝부분은 이렇다.

for (int i = 0; i < n; i++) { write_int(ans[i]); writec('\n'); }
return 0;

풀이. flush_out()이 빠졌다. 버퍼에 남아 있던 마지막 65,536바이트 이하의 내용이 통째로 사라진다.

증상은 출력 크기에 따라 전혀 다르게 나타난다. 예를 들어 ans[i] = i + 1로 두고 각 숫자를 개행하여 출력하면, 버퍼 65,536바이트인 코드의 결과는 다음과 같다.

출력 5줄    → 실제로 나온 줄 수 : 0        (아무것도 안 나온다)
1부터 10만까지 출력 → 나온 줄 수 : 89,232 (마지막 10,768줄 누락)

작은 테스트는 아무것도 안 나오므로 즉시 알아챈다. 위험한 쪽은 큰 출력이다. 버퍼가 가득 찰 때마다 내보내졌으므로 앞의 89%는 멀쩡히 나오고 마지막 한 덩어리만 잘린다. “거의 맞는데 틀린” 상태라 원인을 찾기가 어렵다.

for (int i = 0; i < n; i++) { write_int(ans[i]); writec('\n'); }
flush_out();                 /* ← 이 한 줄 */
return 0;

예방법. 출력 버퍼를 쓰는 코드는 작성하는 순간 flush_out()을 먼저 쓰고 그 위에 루프를 채운다. 순서를 바꾸는 것만으로 이 버그가 사라진다.

흔한 생각무엇이 틀렸나바로잡기
“flush_out()은 나중에 넣어도 되겠지”작은 출력은 아예 안 나오고, 큰 출력은 뒷부분만 잘려 원인을 찾기 어렵다출력 루프를 쓰기 전에 flush_out()부터 적어 둔다
“경고는 에러가 아니니 무시해도 된다”대회 버그의 상당수가 경고로 미리 떠 있던 것이다경고 0개로 만들고 제출한다. -w는 쓰지 않는다
“고속 입력기를 쓰면 무조건 빨라진다”입력이 적으면 차이가 1 ms도 안 난다. 코드만 길어진다100만 개는 예시 규모일 뿐이다. 입력 데이터·제한 시간·실제 측정값을 보고 판단한다
“배열 크기는 입력 받은 n으로 잡자”전역 배열은 크기를 미리 정해야 한다. 실행 중에 바꿀 수 없다제약 조건의 최댓값으로 고정 선언한다. 여유분 몇 칸을 더 잡는다
“fast_in은 복사해 쓰니 내용은 몰라도 된다”음수·long long·단어 읽기로 고칠 일이 반드시 생긴다세 줄(공백 건너뛰기 / 음수 / 자리 올림)의 뜻을 설명할 수 있어야 한다
“지역 배열이 왜 죽는지 모르겠다”메모리 제한(256MB)과 스택 한계(8MB)는 다른 숫자다큰 고정 배열은 전역·정적 영역, 동적 크기는 힙을 먼저 고려한다
“getchar_unlocked가 제일 빠르다던데”C11 표준이 아니라 경고가 나고 환경에 따라 빌드가 안 된다2 ms 때문에 위험을 지지 않는다. fread 버퍼를 쓴다
