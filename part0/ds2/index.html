6연습 문제 해설

01~08은 과정이 보이게 쓰게 하고, 09~10은 실행 결과를 표로 제출받는다.

연습 01 — 빅오로 고치기7점
번호식답버린 것과 그 이유
①7N + 300O(N)계수 7과 상수 300
②2N² + 1000NO(N²)1000N이 커 보여도 N이 500을 넘으면 2N²에 밀린다
③N log N + NO(N log N)N log N이 N보다 크므로 N을 버린다
④500O(1)N과 무관하면 아무리 커도 O(1)
⑤N³ + 2^NO(2N)지수가 다항보다 빠르게 커진다 — N = 30에서 2N은 10억, N³은 2만 7천
⑥N(N+1)/2O(N²)전개하면 (N² + N)/2 → 계수 1/2과 N을 버린다
흔한 오답. ②를 O(N² + N)으로 쓰는 답 — 빅오는 한 항만 남긴다. ⑤를 O(N³)으로 쓰는 답이 가장 많다. N이 작을 때는 N³이 크지만 복잡도는 N이 아주 커졌을 때를 보는 도구이므로 2N이 이긴다. ⑥을 O(N)이라 쓰는 답은 전개를 안 해 본 경우다.
연습 02 — 삼각형 이중 루프6점
for(i=0;i<n;i++) for(j=0;j<i;j++) s++;
정답. i = 0일 때 0번, i = 1일 때 1번, …, i = n−1일 때 n−1번이므로 합은 0 + 1 + 2 + … + (n−1) = n(n−1)/2번. 복잡도는 O(N²).
흔한 오답. “절반만 도니까 O(N²/2)” 또는 “O(N²)보다 빠르니 O(N log N)” — 둘 다 틀렸다. 계수 1/2은 버려지고, 절반이어도 N에 제곱으로 비례한다. N = 100,000이면 4,999,950,000번(약 50억 번)이므로 1초 제한에서는 일반적으로 시간 초과 위험이 매우 크다. 이 오해는 07장 이후 이중 루프 문제마다 반복되므로 여기서 확실히 잡는다.
연습 03 — 빠른 순서로 나열5점
정답. O(1) < O(log N) < O(N) < O(N log N) < O(N²) < O(N³) < O(2N)
흔한 오답. O(N log N)을 O(N²) 뒤에 놓는 답. N = 100,000에서 166만과 100억으로 6,000배 차이다. 헷갈리면 숫자를 대입해 보게 한다. O(2N)을 O(N³)보다 앞에 놓는 답도 있는데, N = 30에서 10억 vs 2만 7천으로 확인시킨다.

연습 04 — N = 100,000에서의 시간 판정(근사)8점
번호복잡도총 연산 횟수모형상 시간*예상 판정
①O(N)100,000 × 1 = 10만약 0.001초대체로 가능
②O(N log N)100,000 × 16.6 ≈ 166만약 0.017초대체로 가능
③O(N√N)100,000 × 316 ≈ 3,160만약 0.32초환경에 따라
④O(N²)100,000 × 100,000 = 100억약 100초대체로 초과

* 모형 계산값: 각 항을 실제 C 명령어 수가 아닌 단위 작업으로 보고 초당 1억 단위 작업을 가정한 값이다. Big-O만으로 실행 시간이 정해지지는 않는다.

채점. 각 2점(횟수 1점 + 판정 및 근거 1점). ③은 근사 기준선 아래에 있지만 코드의 상수·메모리 접근·채점 환경에 따라 결과가 달라질 수 있다. ‘통과 가능하나 보장은 안 됨’을 인정한다. N√N은 제곱근 분할 기법에서도 등장한다.
흔한 오답. ④를 “10억”으로 쓰는 자릿수 실수. 105 × 105 = 1010 = 100억이다. 지수로 먼저 더하고 나중에 한국어 단위로 옮기는 습관을 들이면 사라진다.
연습 05 — 제약 조건에서 역산8점
번호제약대표 권장 복잡도총 연산 횟수대표 풀이
①N ≤ 18O(2N)218 ≈ 26만
O(2N·N)도 470만		부분집합 전부 확인, 비트마스크
②N ≤ 400O(N³)6,400만삼중 루프, 플로이드 워셜
③N ≤ 3,000O(N²)900만이중 루프 DP
④N ≤ 200,000O(N log N)약 350만정렬, 세그먼트 트리
⑤N ≤ 5,000,000O(N)500만한 번 훑기, 누적 합
채점. 각 1.6점. 한 단계 위아래로 답했어도 총 연산 횟수를 계산해 근거를 댔으면 절반을 준다. ③에서 O(N² log N)(약 1억 작업)을 답했다면 단정적인 통과 판정 대신 실제 구현과 시간 제한에 따라 아슬아슬하다는 이유를 요구한다.
지도 포인트. 이 문항의 목적은 암기가 아니라 “N을 대입해 작업량의 규모를 구하고 제한·상수를 함께 살핀다”는 절차다. 표를 외워 쓴 학생과 계산한 학생을 구분하려면, ①을 N ≤ 22로 바꿔 즉석에서 다시 물어본다(222 ≈ 420만, 여전히 가능).

연습 06 — 메모리 계산 (제한 256MB)8점
번호선언원소 × 크기메모리판정메모
①int a[10000000];107 × 4B약 38 MB가능여유 있다
②long long b[50000000];5×107 × 8B약 381 MB불가제한의 1.5배
③int c[3000][3000];900만 × 4B약 34 MB가능2차원도 계산법은 같다
④char d[100000000];108 × 1B약 95 MB가능256MiB 기준 약 161MiB 남음(다른 사용량 제외)
채점. 각 2점(계산 1점 + 판정 1점). 표의 환산은 1MiB = 1,048,576바이트 기준이다(문제의 256MB 표기는 채점 환경의 단위 정의도 확인). 100만 바이트를 1MB로 어림해도 규모 판단에 충분하다. 대회장에서 필요한 것은 정밀도가 아니라 자릿수 감각이다.
흔한 오답. ④에서 char를 4바이트로 계산하는 답. char는 1바이트다. 그래서 값이 0~255 범위라면 unsigned char 배열을 쓰는 것이 안전하다(일반적인 8비트 바이트·4바이트 int 환경에서 원소 저장 공간은 1/4) — 메모리가 빠듯할 때 쓰는 실전 기법이다.
연습 07 — 7.6MB인데 왜 죽었나6점
정답. main 안에 선언한 지역 변수는 스택(stack)이라는 별도의 좁은 공간에 놓인다. 스택은 보통 운영체제와 실행 환경마다 크기 제한이 따로 정해져 있으며, 어떤 환경에서는 7.6MiB 크기의 지역 배열이 스택 한도를 넘어 스택 오버플로를 일으킬 수 있다. 전체 메모리 제한이 256MB여도 스택이 그만큼 허용되는 것은 아니다.

해결 방법 두 가지.

  • 전역으로 옮긴다 — 함수 바깥에 static int a[2000000];으로 선언한다. 덤으로 전역 배열은 0으로 초기화된다(정적 저장 기간).
  • 동적 할당한다 — #include <stdlib.h>를 포함하고 int *a = malloc(2000000 * sizeof *a);로 동적 할당한다. NULL 여부를 검사하고 사용 후 free(a)를 호출한다. 05장 동적 배열에서 다시 다룬다.
지도 포인트. 증상이 특이하다. 입력을 읽기도 전에 죽기 때문에 학생은 “입력이 잘못됐나” 하고 엉뚱한 곳을 본다. “실행 직후 오류가 나면 큰 지역 배열과 스택 한도를 먼저 점검하라”를 34장 디버깅 체크리스트에 그대로 싣는다. 올림피아드에서는 크고 크기가 정해진 배열은 전역·정적 저장 기간을 우선 검토하고, 입력에 따라 크기가 달라지면 동적 할당도 고려하게 한다.

연습 08 — 50N log N 과 N²8점

(1) 비슷해지는 N. 50 N log₂N = N² 양변을 N으로 나누면 50 log₂N = N. 몇 개 대입해 본다.

NA : 50 N log₂NB : N²유리한 쪽
100약 33,00010,000B
400약 173,000160,000B
440약 193,000193,600거의 같음
1,000약 500,0001,000,000A

따라서 N ≈ 440 부근에서 뒤집힌다. “400~500 사이”라고 답해도 정답이다.

(2) N = 1,000,000일 때. A = 50 × 106 × 19.9 ≈ 10억, B = 1012. A가 약 1,000배 빠르다.
그런데 여기서 멈추면 안 된다. A도 약 10억 단위 작업에 해당하므로 1초 제한에서 안전하다고 보기 어렵다. 복잡도를 N log N으로 맞췄는데도 상수 50 때문에 떨어지는 경우이고, 이럴 때 비로소 2.5절의 “상수를 줄이는 싸움”이 시작된다.
채점. (1) 3점 — 대입표를 만들었으면 값이 조금 달라도 정답. (2) 5점 중 3점은 1,000배, 나머지 2점은 “A도 1초 통과를 보장할 수 없다”를 지적했는지에 준다. 이 지적을 한 학생은 복잡도를 도구로 쓸 줄 아는 것이다.
연습 09 — 이분 탐색 비교 횟수 실험7점
$ ./counter   (n을 바꿔 가며 실행, key = n-1 인 최악의 경우)
n=      1000   이분탐색 비교=10    log2(n)= 9.97
n=    100000   이분탐색 비교=17    log2(n)=16.61
n=   1000000   이분탐색 비교=20    log2(n)=19.93
해석. 이 예처럼 범위가 양끝을 포함하고 중간 인덱스를 내림하여 계산하는 표준 이분 탐색에서, 최악의 비교 횟수는 ⌊log₂n⌋ + 1 = ⌈log₂(n+1)⌉이다. ⌈log₂n⌉와 항상 같은 것은 아니다(예: n = 1,024이면 최악 11회). 특정 키를 찾는 횟수는 위치에 따라 더 적을 수 있다. 제시된 key = n-1 예에서는 n = 1,000 → 10회, n = 1,000,000 → 20회다.
채점. 표 3점 + 해석 4점. “일치한다”라고만 쓴 답은 절반. 정확한 최악 횟수의 식과 조건을 짚은 답에 만점. 값이 ±1 다른 것은 찾는 값의 위치 차이이므로 감점하지 않되, 교재대로 key = n-1(최악)로 측정했는지 확인한다.

연습 10 — O(N²) 시간이 몇 배로 늘어나는가7점
다음은 설명용 측정 예시 — PC·컴파일러에 따라 수치가 달라짐
N=  25000   O(N^2) 시간 =    96.5 ms   (쌍 3.1억개)
N=  50000   O(N^2) 시간 =   429.3 ms   (쌍 12.5억개)
N= 100000   O(N^2) 시간 =  1378.3 ms   (쌍 50.0억개)
N의 변화이론 배율예시 배율판정
25,000 → 50,0004배429.3 ÷ 96.5 = 4.4배이론과 잘 맞는다
50,000 → 100,0004배1378.3 ÷ 429.3 = 3.2배약간 작지만 4배에 가깝다
해석. N이 두 배가 되면 이론적인 반복 횟수는 약 네 배로 증가한다. 위의 값은 원리를 설명하기 위한 예시이지 모든 환경에서 재현되는 보장값이 아니다. 실제 시간 배율에는 컴파일러 최적화, 캐시, CPU 클록, 다른 프로세스, 측정 방법이 영향을 준다. 한 번의 측정값으로 성능을 확정하지 말고 여러 번 측정해 중앙값과 증가 추세를 비교한다. 예시에서 N = 100,000의 1.38초 역시 해당 예시 조건에서만 의미가 있다.
실험 함정 — 시간이 0.0 ms로 나오면? 실행이 너무 짧아 시계의 해상도에 묻혔거나, 결과가 관찰되지 않는 계산을 컴파일러가 제거했을 가능성이 있다. 단순히 printf를 추가하는 것만으로 모든 최적화가 막히지는 않는다. 아래처럼 반복마다 관찰 가능한 volatile 변수에 값을 누적하면 루프 제거를 막는 데 도움이 된다. 단, volatile 접근 자체에 비용이 있으므로 이 실험은 반복 횟수의 증가 경향을 확인하는 용도로 쓴다.
/* 함수 안에서 사용하는 유효한 C11 코드 예시 */
volatile unsigned long long g = 0;
for (int i = 0; i < N; ++i) {
    for (int j = 0; j < i; ++j)
        g += (unsigned long long)((i ^ j) & 1);
}
printf("(검증용 %llu)\n", g);

이 함정이 알려 주는 것

컴파일러는 프로그램 결과에 영향을 주지 않는 계산을 없앨 수 있다. 관찰 가능한 결과를 유지하고, 충분히 큰 입력으로 반복 측정하도록 지도한다. 이 예제의 volatile은 제거 방지용 실험 장치이며 일반 알고리즘 코드에 무분별하게 사용하지 않는다. 34장 디버깅 단원에서 다시 등장한다.

같은 문제를 쉬운 버전과 어려운 버전으로 나누어 부분 점수 구조를 만들기 위해서다. 채점 결과는 세 갈래로 갈린다.
· 문제를 아예 못 푼 학생 → 둘 다 실패
· 느린 풀이(이중 루프)를 떠올린 학생 → A만 통과, 절반의 점수
· 빠른 풀이를 찾아낸 학생 → 둘 다 통과, 만점
출제자 입장에서는 한 문제로 “아이디어는 있는가”와 “효율까지 생각했는가”를 동시에 물을 수 있다. 올림피아드에서 매우 흔한 출제 방식이므로, 어려운 버전이 안 풀리면 쉬운 버전이라도 확실히 받아 두는 전략을 함께 가르친다.

(3) 내 풀이의 복잡도 추정 — 4점

두 판정만으로 실제 알고리즘의 빅오를 유일하게 결정할 수는 없다. 같은 O(N log N)도 구현 상수가 크면 B에서 실패할 수 있고, 메모리·입출력 문제일 수도 있다. 다만 시간 초과가 원인이고 단순한 작업량 모형을 가정한다면, A에서 약 100만 작업인 O(N²), B에서 약 3.5억 작업인 O(N√N) 등의 풀이를 유력 후보로 의심해 볼 수 있다. 먼저 구현의 반복 구조와 실제 연산 수를 확인해 원인을 좁힌다.
채점. (3)에서 “O(N²) 가능성이 있다”는 근거를 제시하면 3점, 두 통과 결과만으로 복잡도를 확정할 수 없다는 한계까지 설명하면 4점. 이것이 대회장에서 시간 초과를 받았을 때 실제로 해야 하는 사고 과정이다.

7도전 문제 해설 (이어서)

도전 C2 — 복잡도가 거짓말을 할 때15점

(1) 두 프로그램의 복잡도 — 2점

둘 다 원소를 하나씩 정확히 한 번 읽으므로 모두 O(N)이다.

(2) 왜 시간이 다른가 — 7점

CPU는 메모리에서 값을 하나만 가져오지 않고 주변 값까지 한 덩어리로 가져다 가까운 곳에 보관한다(캐시).
· P(배열) — 주소가 연속이라 한 번 가져올 때 다음에 쓸 값들이 함께 따라온다. 이후 접근은 대체로 캐시 덕분에 빨라질 수 있다.
· Q(연결) — 노드가 흩어져 있어 매번 먼 곳에서 새로 가져와야 한다. 게다가 다음 노드의 주소를 읽어야만 그다음으로 갈 수 있어 메모리 지연을 숨기기가 상대적으로 어렵다.
빅오는 “몇 번 접근하는가”만 세고 “한 번 접근이 얼마나 비싼가”는 세지 않는다. 그 차이가 상수로 나타난다.

(3) 교훈 한 문장 — 6점

모범 답안 — “복잡도와 연산 조건이 비슷하다면 연속 메모리 배치를 우선 검토한다.”
연속 배열은 캐시 지역성에서 유리한 경우가 많다. 다만 중간 삽입·삭제, 메모리 사용, 실제 연산 패턴에 따라 연결 구조가 더 적합할 수도 있다. 09장의 노드 풀이나 29장의 배열 기반 그래프 표현도 지역성을 고려하는 설계 예다.

(4) 측정값 예시 — 가산점 최대 5점

설명용 예시 (N = 2,000,000, 연결 노드의 접근 순서가 무작위인 경우)
 P 배열 순차 읽기 :     0.7 ms
 Q 연결 따라가기  :    88.2 ms   -> 약 126배 느림

위 수치는 재현을 보장하지 않는 비교 예시이다. 반복 측정해 원인과 차이를 설명하면 3점, 노드 할당·접근 순서가 캐시 효과에 미치는 영향까지 분석하면 추가 2점을 준다. 차이의 배율 자체를 정답 조건으로 삼지 않는다.

채점. (3)은 “배열이 빠르다”로 끝나면 3점. “복잡도와 실제 연산 조건이 비슷할 때”라는 조건을 붙인 답에만 만점을 준다. 조건 없이 “배열이 항상 빠르다”로 쓰면 01장에서 배운 중간 삽입 O(N)을 잊은 것이므로 반드시 바로잡는다.
